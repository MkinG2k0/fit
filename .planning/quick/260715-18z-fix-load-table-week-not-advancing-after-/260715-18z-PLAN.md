Root cause: `hasSession` uses strict `exercise.catalogExerciseId === trimmedId` only. Merge/analytics use `catalogExerciseId ?? id` (`computeExerciseMergeStats.resolveCatalogId`); `findLastExerciseSession` also falls back to normalized exercise name. Legacy or incomplete journal cards (missing `catalogExerciseId`) never increment `sessionCount`, so `currentWeek` stays 1 forever despite logged days — matches user report for «Жим ногами».

Fix in this file only (FSD entity lib), keep formula and createdAt window from 260715-0qr D-01:
1. Keep `currentWeek = min(16, Math.floor(sessionCount / 2) + 1)` and inclusive scan from `createdAt` start-of-day through today. Do not invent calendar-week progression.
2. Add optional third argument `exerciseName?: string` (or equivalent options object) for name fallback; default behavior without name remains id-based.
3. Match a journal exercise if either:
   - `(exercise.catalogExerciseId ?? exercise.id).trim() === trimmedId` (same resolve pattern as merge helpers), OR
   - when `exerciseName` is non-empty after trim: normalize both names (trim + lower case, same spirit as `findLastExerciseSession.normalizeExerciseName`) and compare equal.
4. Still require `exerciseHasLoggedSets` (any set with reps &gt; 0 or weight &gt; 0) before counting the calendar day once.
5. Do not change storage APIs or week formula; minimal diff.
